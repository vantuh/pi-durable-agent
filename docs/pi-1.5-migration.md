# Pi 1.5 migration

How `pi-durable-agent` moves from Pi 1.4.0 to 1.5.0: what changes, what we gain, what breaks in our
code, and the order of the work. This is [Phase 4 of the refactor plan](refactor-plan.md#phase-4-pi-15).

Sources: the 1.5.0 sections (2026-11-02) of the `pi-durable`, `pi-ai` and `chord` changelogs, and
our code at the commit this file was written against. Every claim carries a mark:

- **(V)** verified: seen in our code, or stated in the changelog text.
- **(I)** inferred: follows from the two, but nothing says it outright. Check it when you reach it.

## Part 1: Documentation

### What upgrades

Six packages go from 1.4.0 to 1.5.0 in one change, each pinned exactly:

- `@earendil-works/pi-durable`
- `@earendil-works/pi-ai`
- `@earendil-works/pi-coding-agent`
- `@earendil-works/chord`
- `@earendil-works/pi-codemode` (`extensions/codemode`) and `@earendil-works/pi-mcp` (`extensions/mcp`).
  The first draft of this file counted four, but its 56 pins included these two. pi-durable 1.5.0
  pins `pi-codemode` 1.5.0 exactly, and a 1.4.0 copy next to it would be a second one.

They appear in the root `package.json:19-22` and in 31 `package.json` files at the root and under
`extensions/*` (56 pins in total) (V). `@earendil-works/pi-schema` 1.5.0 arrives as a transitive
dependency; we do not declare it (V: the changelogs say `typebox` left pi-durable, pi-ai and chord and
pi-schema took its place).

The packages move together because pi-durable 1.5.0 pins `chord`, `pi-ai`, `pi-codemode`, `pi-schema` and `pi-telemetry` at 1.5.0 exactly (V: its `package.json`; `pnpm why` lists one version of each of our six packages after the bump). A second chord copy would give
two `Context` implementations, and `withCancel` (`extensions/bash-timeout/server.ts:124`) and
`BACKGROUND_CONTEXT` could stop matching across them (I). The 1.5.0 changelogs do not list either as
changed (V: no entry for them in the three sections).

The version also appears in prose: `AGENTS.md:44` and `docs/stack.md:24` say "1.4.0". Update both with
the bump.

### Data

We only go forward. 1.5 migrates 1.4's `pi.live` when it reads it (version 1 to 2 to 3), and 1.4
cannot read what 1.5 wrote: `pi.live` versions 2 and 3, `pi.tool` version 3 and `pi.generation`
version 2 leave an older Harness's tasks blocked (V: changelog entries on `pi.live`, `pi.tool`,
`pi.generation`).

Changes you will notice without a code change (V, changelog):

- Reads are frozen. `tx.task()`, `tx.conversation()`, `getTask()`, `runtime.entry()` and published
  entries are shared with Durable's caches, and mutating one throws. We have no known mutation of
  such a value (I); the test run in step 4 will show one.
- A compaction no longer hides what came before it in the view. Head markers stay where they are
  and the window is by entry id, so the transcript can show entries from before a compaction.
- A Harness-written error result (`tool_unavailable`, `invalid_arguments`, `blocked`, `interrupted`,
  `restart_limit`, `aborted`) now goes through `afterTool`. See the table below.
- Watches coalesce the commits made while a listener runs into one callback. `host.onCommit` listeners
  can receive fewer calls than there were commits (I).

**Not in 1.5.0**, though the brief and some issue numbers suggest it: these sit under `[Unreleased]` in
the changelogs (V).

- pi-ai: Anthropic message threads and `StreamOptions.disableContinuation`.
- pi-ai: Anthropic non-strict tool schemas dropping root `$defs` (#9557). It would help MCP servers, but
  `extensions/mcp/server.ts:81` registers one proxy tool whose `arguments` is a free record, so it
  would not have reached us in any case (I).
- pi-durable: a cheaper `SqliteStorage.commit()`.

### What it lets us delete or simplify

- **`hasOlder` and the retry loop in `stream()`.** `server/history.ts:18` `hasOlder`, the `while` loop
  in `server/main.ts:598` `stream()` and `server/main.ts:338` `firstEntryId` exist to learn whether
  older entries exist, and have to be retried because a commit can land during the read. `view.before`
  is that answer, and it is part of the same value the page is cut from (V: changelog, "the ID of the
  entry just before the window"). `more` becomes `page.cut || view.before !== undefined`. `entryAt`
  and `historyPage` in the same file stay: they page the log for `/api/history`.
- **`helloPage` and `HELLO_BYTES`** (`server/main.ts:82`, `:309`). The window caps the number of
  entries, not their size, so a window of 100 large entries can still exceed the 128 KB the cut
  protects (I). Measure the largest projected window on real sessions first (step 6). Delete the cut
  only if the window stays small; otherwise keep it as a byte trim of the window.
- **`docs/server.md`.** "The view is not the whole conversation" (line 46) describes a view that
  starts at the newest head marker. That is no longer true. The diagram at line 9, "Why the view, not
  the callbacks" (line 25, `root.viewState()`) and "Bytes over a slow link" (line 31) name the old
  API or the old cut and are rewritten in step 6.
- **`setImmediate` in `server/new-conversations.ts:19`.** Keep it. The comment says the listener
  must not call the Session, and the changelog says an `observeCommits` observer runs one microtask
  after the commit, before the waits it resolves (V). It does not say that an observer may call the
  Session, and `observe` does (`attach(id)` at `server/main.ts:917`). Dropping the indirection would
  be a guess (I).
- **`opened.sent`** (`server/main.ts:565`, `publish`) can shrink from an array of ids to the newest
  id sent, because ids only grow (I). Part of step 4.

### TypeBox

In 1.5 a tool's `parameters` is any JSON Schema object, typed through `@earendil-works/pi-schema`.
TypeBox schemas are JSON Schema, so they still validate. Six extensions import TypeBox directly and
declare it themselves, pinned at `1.3.27`: `bash-timeout` (a dev dependency, used by its test),
`browser`, `mcp`, `subagents`, `web-fetch` and `web-search` (V: each `package.json`). Nothing else
provides it once pi-ai and pi-durable stop depending on it, so these declarations stay until the move.
The move to pi-schema builders (`obj`, `str`, `num`) was a separate, optional phase, now done:
[pi-schema-migration.md](pi-schema-migration.md). No extension declares `typebox` any more.

## Part 2: Migration plan

Steps 2 to 4 do not ship alone. Once the packages are bumped the tree does not compile until the
watch port is done, so commit them one concern at a time, and read the `tsc` errors after step 2 as
the to-do list. Steps 5 to 8 each leave a green tree. Do this after the Hono and Zod phases (done)
and before `server/main.ts` is split into `server/streams/`: the split would otherwise carry the old
view code into a new file and then change it there.

- [ ] **1. Prepare the data.** The owner's step, not part of the code change. A worktree has its own
      empty `data/` (`data/` is gitignored), so the only database that matters is the main repo's
      `data/state.sqlite`: copy it **before the main server first starts on 1.5**, that is, after the
      merge and before the main server is restarted. The code change was tried on a scratch copy only.
    - Files: `data/state.sqlite`, `data/state.sqlite-wal`, `data/state.sqlite-shm` of the main repo.
